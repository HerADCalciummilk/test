# L1 机器审核规范

本文档描述本仓库当前已落地的 **L1（机器）算法上传审核** 规则、触发方式、结果产出与处置要求。  
实现代码位于 `.github/scripts/review/`，工作流为统一入口 `.github/workflows/algorithm-review.yml` 中的 **job `l1`**（`L1 machine review`）。  
规则以代码为准；若文档与代码不一致，以 `rules.py` / `l1_review.py` 为准并应回写本文档。

目录结构约定对齐算法仓库 `CODEX.md`（必要子目录：`src`、`cli`、`test`、`docs`、`nbs`、`resource`）。

> L2（LLM）见 [L2_LLM审核规范.md](./L2_LLM审核规范.md)。同一 workflow 内 **L1 成功后才跑 L2**，避免并行重复。

---

## 1. 目标与范围

| 项目 | 说明 |
| ------ | ------ |
| 门禁级别 | L1（纯机器检查，不含人工签核、不含 LLM） |
| 审核对象 | PR 变更所涉及的算法包 |
| 包路径 | `00temp/<算法名>/`（中间整理目录）或 `NIMM/<算法种类>/<算法名>/`（正式归档目录） |
| 不在范围内 | 大体积二进制样例数据（如 `.nc`/`.grib` 等跳过内容扫描）、人工 checklist、LLM 语义评审 |

L1 之后可扩展 L2（LLM）、L3（人工）；本文档仅覆盖 L1。

---

## 2. 触发与执行流程

### 2.1 何时运行

- **创建或更新 Pull Request**（GitHub 事件 `pull_request`）→ 工作流 `Algorithm review`  
  - 「打开」= 新建 PR（例如点 Create pull request）  
  - 「更新」= 向该 PR 所属分支再次 `push`、或 Re-run 等再次触发同一类事件  
- **在 Actions 页手动触发**（`workflow_dispatch`）  
  - 当前 **不会**传入 `--base` / `--path`  
  - 因此识别不到算法包：`packages` 为空，通常无阻断；适合验证 workflow 能否跑通，不适合代替 PR 审核  
- **与 L2 的顺序**：同一 run 内先执行 job `l1`；仅当 L1 **成功**（无 blocker）后才执行 job `l2`

### 2.2 扫描范围（PR 场景）

1. 计算相对 PR 基线（`base.sha`）的 **变更文件列表**（`git diff --name-only`）  
2. **根据变更文件路径解析算法包根**（是的：改包内任意一个文件即可定位到包）：  
   - `00temp/<pkg>/...` → 包根 `00temp/<pkg>`  
   - `NIMM/<kind>/<pkg>/...` → 包根 `NIMM/<kind>/<pkg>`  
3. 包根下存在 `src/` 或 `cli/` 时，视为算法包，并对该包做 **整包检查**（目录结构 + 插件形态 + 包内文件内容规则 + flake8），不只检查你改过的那一个文件  
4. 若变更文件落在算法包路径之外（且解析不出包），则仅对变更文件做内容类规则扫描（凭据、硬编码路径等），不做「必要目录」整包结构检查  

### 2.3 本地命令

```bash
pip install -r .github/scripts/review/requirements.txt
python .github/scripts/review/l1_review.py --path 00temp/demo_algo_clean --json l1-review.json
python .github/scripts/review/format_l1_comment.py --json l1-review.json --out l1-review-comment.md --attempt 1
```

- `--json l1-review.json`：**会在当前仓库根目录写出/覆盖** `l1-review.json`（可用其他路径；该文件已在 `.gitignore` 中，默认不会提交）  
- `format_l1_comment.py` 会再写出 `l1-review-comment.md`（同样可本地预览评论正文，默认已 gitignore）  
- `--path` 可重复，指定多个包；本地指定路径时不依赖 git 变更列表，直接整包检查  

### 2.4 结果处置流水线（PR）

1. 运行检查 → 写出 `l1-review.json`  
2. 上传 Artifact：`l1-review-report-<run_id>`（含 `l1-review.json`；若本趟会发评论则还有 `l1-review-comment.md`）；该 Artifact 同时作为 L2 的输入  
3. **当事件为 `opened`（Create PR）或 `synchronize`（新 push），且 `run_attempt == 1`（非 Re-run）时**：渲染评论并**追加**一条（不覆盖历史）  
4. 若存在 **阻断项（blocker）** → job `l1` 失败（Checks 红灯），**不进入 L2**；仅有警告则 L1 绿灯并继续 L2  

说明：Checks 里 **Re-run**、手动 `workflow_dispatch` **不会**追加评论；检查与 Artifact 仍会执行（PR 场景下）。  
分支保护请勾选必过检查 **`L1 machine review`**（或 `Algorithm review / l1`，以 GitHub 展示名为准）；旧名 `L1 review` 已废弃。

## 3. 严重级别定义

| 级别 | 英文 | 对 Checks 的影响 | 对合并的影响 |
|------|------|------------------|--------------|
| 阻断 | `blocker` | 失败（红灯） | 若分支保护要求本检查通过，则不可合并 |
| 警告 | `warning` | 不单独失败 | 可合并，但应修复后再入库 |

评论与 `l1-review.json` 中均会列出全部阻断项与警告项。

## 4. 必要目录（结构门禁）

每个算法包（无论中间目录还是正式目录）**必须同时具备**以下子目录：

| 目录 | 用途（与 CODEX 一致） |
| ------ | ------------------------ |
| `src/` | 核心算法 / 插件源码 |
| `cli/` | 调度与预处理入口 |
| `test/` | 单元测试 |
| `docs/` | 说明文档 |
| `nbs/` | notebook 示例 |
| `resource/` | 资源与小规模测试用资源（可先空目录 + `.gitkeep`） |

可选（当前 L1 **不**强制）：`utils/`、`test_data/`（测试数据建议放独立 testdata 仓）。

| 规则 ID | 适用路径 | 级别 |
|---------|----------|------|
| `MISSING_REQUIRED_DIR` | `00temp/<pkg>/` | **阻断** |
| `MISSING_REQUIRED_DIR_OFFICIAL` | `NIMM/<kind>/<pkg>/` | **阻断** |

缺任一必要目录即记一条对应规则（message 中列出缺失目录名）。

### 4.1 必要目录实质内容（warning）

在**目录已存在**的前提下（缺目录仍由上一节 blocker 处理，不再重复检查）：

| 情况 | 级别 | 说明 |
|------|------|------|
| 本层无任何文件，且无子目录 | `EMPTY_REQUIRED_DIR` warning | 空目录 |
| 本层仅有 `.gitkeep` 等占位文件 | `EMPTY_REQUIRED_DIR` warning | 仅占位，无实质文件 |
| 本层有非占位文件，或存在非 skip 子目录（如 `src/utils/`） | 通过 | `cli/` 仅含 `__init__.py` + `__main__.py` 亦算有内容 |

不递归扫描子目录内文件；子目录存在即视为该层非空。

## 5. 规则一览

### 5.1 阻断项（blocker）

| 规则 ID | 标题 | 检查要点 |
| --------- | ------ | ---------- |
| `CREDENTIAL_PATTERN` | 疑似凭据或私钥 | 文本中出现 PEM 私钥头（`BEGIN … PRIVATE KEY`）或典型 AWS Access Key 形态（`AKIA` + 16 位） |
| `MISSING_REQUIRED_DIR` | 中间目录缺少必要子目录 | 见第 4 节 |
| `MISSING_REQUIRED_DIR_OFFICIAL` | 正式目录缺少必要子目录 | 见第 4 节 |
| `NO_CONCRETE_PLUGIN` | 未找到具体插件类 | `src/`（跳过 `utils`）中无（直接或间接）继承 `BasePlugin` / `PostProcessingPlugin` 的具体插件类；**00temp 与 NIMM 均为阻断** |
| `PLUGIN_MISSING_INIT` | 具体插件缺少 `__init__` | 已识别的具体插件类未定义 `__init__`（无参可空实现） |
| `PLUGIN_MISSING_PROCESS` | 具体插件缺少 `process` | 已识别的具体插件类未定义 `process` |
| `PLUGIN_EMPTY_PROCESS` | 具体插件 `process` 为空 | `process` 仅有 docstring / `pass` / `...` |
| `PYTHON_SYNTAX_ERROR` | Python 语法错误 | 包内（或包外变更的）`.py` 无法被 `ast.parse` 解析；导入/运行必失败 |

### 5.2 警告项（warning）

| 规则 ID | 标题 | 检查要点 |
| --------- | ------ | ---------- |
| `HARDCODED_BIZ_PATH` | 硬编码业务路径 | 出现 `/home/nimm` 或 `/home/<user>/nimm` 一类路径 |
| `PLUGIN_FILE_IO` | src 中疑似文件 I/O | `src/**/*.py` 非注释行出现 `open(`、`read_csv(`、`to_csv(`、`Path(...).write` 等 |
| `UNDECLARED_NATIVE_BINARY` | 未说明的二进制扩展 | 包内存在 `.so` / `.pyd` / `.dll`，且 `docs/` 中未提及该文件名或后缀 |
| `FLAKE8` | flake8 风格、格式与命名问题 | 对纳入扫描的 `.py` 跑 flake8（**行宽 120**）+ **pep8-naming**；含缩进/行宽等，以及类名须 CapWords（`N801`）、函数名小写（`N802`）等 PEP 8 命名约定；**不再使用 Black** |
| `PLUGIN_BASE_CHAIN` | `PostProcessingPlugin` 未继承 `BasePlugin` | 包内定义的中间基类未直接继承 `BasePlugin` |
| `EMPTY_REQUIRED_DIR` | 必要目录无实质内容 | 目录已存在但本层无文件，或仅有 `.gitkeep` 占位（缺目录为 blocker，不重复检查） |

说明：

- **中间目录 `00temp/` 与正式目录 `NIMM/` 均须满足插件基础形态**（具体插件类 + `__init__` + 非空 `process`），不满足为阻断。  
- 插件 I/O、硬编码路径在业务迁移期仍可能出现，故暂为警告；正式入库前应清理。  
- 风格/格式/命名统一以 flake8（含 pep8-naming）为准，建议修复，当前不阻断。  
- 类名须采用 CapWords（大驼峰，如 `ApplyBiasCorrection`）；由 pep8-naming 的 `N801` 检查。  
- **插件形态（L1）**：审「（直接或间接）继承 `BasePlugin`/`PostProcessingPlugin` 且类名不是这两个基类」的具体类（如 `Foo(BasePlugin)` 与 `AfterFoo(Foo)` 均算）；基类本身不要求业务级 `process`；`src/utils` 参与继承解析但不要求形态。  
- 禁止用空 `process` 凑检；包内应至少有一个具体插件。  
- 在「识别到算法包」时，flake8 作用范围为**该包内所有被扫描到的 `.py`**（整包）。

## 6. 扫描与忽略策略

| 策略 | 说明 |
| ------ | ------ |
| 跳过目录名 | `.git`、`__pycache__`、`.ipynb_checkpoints`、`.pytest_cache`、`.mypy_cache`、`node_modules` |
| 跳过后缀（不做文本规则扫描） | `.pyc`、图片、`.nc`、`.grib`、`.grb` 等 |
| 单文件大小上限 | 超过约 1MB 的文本不读入做内容规则匹配 |
| 注解 | 在 Actions 日志 / Checks Annotations 中输出 `::error`（阻断）或 `::warning`（警告） |

## 7. 报告与审计产物

### 7.1 `l1-review.json`（机器可读）

主要字段：

```json
{
  "gate": "l1",
  "packages": ["00temp/demo_algo_issues"],
  "summary": { "blocker_count": 1, "warning_count": 2 },
  "blockers": [
    {
      "rule_id": "MISSING_REQUIRED_DIR",
      "severity": "blocker",
      "path": "00temp/demo_algo_issues",
      "line": null,
      "message": "缺少必要目录: test, nbs, resource"
    }
  ],
  "warnings": []
}
```

### 7.2 PR 评论（人可读时间线）

- 在 **Create PR**（`opened`）或向该 PR 分支 **新 push**（`synchronize`）时追加一条评论；**Re-run 不发评论**  
- 不覆盖历史评论；标题含「第 N 次」；正文含 **检查时间（北京时间 +0800）**、状态、包列表、阻断/警告摘要、**提交 SHA**、**Actions 运行链接**  
- 隐藏标记：`<!-- nimm-l1-review -->`（用于统计次数，不对用户展示）

字段含义：

| 评论字段 | 含义 |
| ---------- | ------ |
| 提交 | 本次检查对应的 Git commit SHA（代码版本） |
| Actions 运行 | 本次 workflow run 页面；可下该次 Artifact |
| run_id | Actions 运行数字 ID，出现在 Artifact 名 `l1-review-report-<run_id>` 中 |

### 7.3 Artifact

- 名称：`l1-review-report-<run_id>`  
- 内容：该次运行的 `l1-review.json`、`l1-review-comment.md`  
- 保留：默认随 GitHub Artifact 策略（通常约 90 天）；**每一次 run 各自一份**，不是只保留最近一次  
- 历史回顾：打开对应次数评论里的 Actions 链接，或在 Checks 中点开历史运行

## 8. 开发者处置要求

1. **有阻断**：必须修复后再次 push；Checks 变绿前不应合并（建议开启分支保护强制本检查）。阻断项含必要目录、插件基础形态（具体插件 / `__init__` / 非空 `process`）等。  
2. **仅有警告**：Checks 可通过，但仍应在合并前尽量消除（尤其硬编码路径、src 内文件 I/O、基类继承链等）。  
3. **回溯**：按 PR Conversation 时间线阅读历次 L1 评论，对照提交 SHA 与 Artifact。
