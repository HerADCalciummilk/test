# L1 机器审核规范

本文档说明本仓库 **L1（机器）算法上传审核** 的行为：触发方式、包识别、目录与插件规则、报告格式及处置要求。

- 实现代码：`.github/scripts/review/`（入口 `l1_review.py`，规则 `rules.py`）
- CI 入口：`.github/workflows/algorithm-review.yml` 中的 job **`l1`**（Checks 名称 **`L1 machine review`**）
- 目录约定：与算法仓库 `CODEX.md` 一致（见下文第 3 节）
- 语义审核（LLM）：见 [L2_LLM审核规范.md](./L2_LLM审核规范.md)

若文档与代码不一致，以 `rules.py`、`l1_review.py` 为准，并应同步更新本文档。

---

## 1. 职责与边界

L1 是纯机器检查：结构、语法、插件形态、密钥与部分内容模式、flake8 风格等。**不含** LLM 语义审、**不含**人工签核。

| 项目 | 说明 |
|------|------|
| 严重级别 | **blocker**（Checks 失败）与 **warning**（记录但不单独令 job 失败） |
| 审核输入 | PR 相对基线的变更文件列表，或由 `--path` 指定的路径 |
| 输出 | `l1-review.json`、PR 评论（条件见第 8 节）、Actions 注解 |

同一 workflow 中，job `l2` 在 job `l1` **成功**（无 blocker）后执行。

## 2. 算法包识别

### 2.1 两类布局

**中间目录（整理期）**

```text
00temp/<pkg>/
  src/ cli/ test/ docs/ nbs/ resource/
```

**正式目录（归档后）**

```text
NIMM/<kind>/<pkg>/              # 源码根（插件扫描根）
cli/<kind>/<pkg>/               # 调度入口
test/<kind>/<pkg>/
docs/<kind>/<pkg>/
nbs/<kind>/<pkg>/
resource/<kind>/<pkg>/
```

正式算法的稳定标识为 **`NIMM/<kind>/<pkg>`**。配套目录与 `NIMM` 位于仓库根同级，源码直接放在 `NIMM/<kind>/<pkg>/` 下，不要求其内再建 `src/` 或 `cli/`。

### 2.2 从变更路径解析包

| 变更路径前缀 | 识别结果 |
|--------------|----------|
| `00temp/<pkg>/...` | 中间包 `00temp/<pkg>` |
| `NIMM/<kind>/<pkg>/...` | 正式包 `NIMM/<kind>/<pkg>` |
| `cli\|test\|docs\|nbs\|resource/<kind>/<pkg>/...` | 同上正式包 |
| `NIMM/utils/...` | 公共库，**不**识别为算法包 |
| `NIMM/<kind>/...`（无 pkg 层） | 不识别为算法包 |
| 其它路径 | 不识别为算法包 |

### 2.3 纳入整包检查的条件

**中间包**：路径可解析为 `00temp/<pkg>`，且包内存在 **`src/` 或 `cli/`** 目录之一。若路径像中间包但两者皆无，记 **`PACKAGE_NO_ENTRY_DIR`**（blocker），不做整包检查。

**正式包**：路径命中第 2.2 节正式包规则即纳入整包检查。

**整包检查包括**：必要目录结构、空目录警告、插件形态、二进制说明、相关树下文件内容规则、flake8。

### 2.4 未识别为算法包时的检查

变更落在算法包路径之外（含 `NIMM/utils`、文档、CI 脚本等）时，对**本次变更的文件**执行：

- 语法、凭据、硬编码路径、flake8
- `NIMM/**` 下 `.py` 的疑似文件 I/O（`PLUGIN_FILE_IO`）
- 危险 API 模式（`DANGEROUS_API`）
- **弱插件检查**：仅在本次变更的 `.py` 文件集合内解析继承关系，检查具体插件类的 `__init__` / `process`（不要求「包内至少一个具体插件」）

L2 会对这些变更文件调用 LLM（见 L2 规范）；L1 本身不做语义审。

## 3. 必要目录（结构门禁）

### 3.1 中间包 `00temp/<pkg>/`

须同时存在以下**包内**子目录（缺任一为 blocker，规则 **`MISSING_REQUIRED_DIR`**）：

| 目录 | 用途 |
|------|------|
| `src/` | 插件与算法源码 |
| `cli/` | 调度入口 |
| `test/` | 单元测试 |
| `docs/` | 说明文档 |
| `nbs/` | notebook |
| `resource/` | 资源（可先 `.gitkeep`） |

### 3.2 正式包 `NIMM/<kind>/<pkg>`

须同时存在以下六处路径（缺任一为 blocker，规则 **`MISSING_REQUIRED_DIR_OFFICIAL`**）：

| 路径 | 用途 |
|------|------|
| `NIMM/<kind>/<pkg>/` | 源码根 |
| `cli/<kind>/<pkg>/` | 调度入口 |
| `test/<kind>/<pkg>/` | 单元测试 |
| `docs/<kind>/<pkg>/` | 说明文档 |
| `nbs/<kind>/<pkg>/` | notebook |
| `resource/<kind>/<pkg>/` | 资源 |

`NIMM/utils/` 等为公共库，L1 不对其做上述六树整包门禁。

### 3.3 目录实质内容（warning）

对**已存在**的必要目录（缺目录由上一节 blocker 处理）：

| 情况 | 规则 | 级别 |
|------|------|------|
| 本层无文件且无子目录 | `EMPTY_REQUIRED_DIR` | warning |
| 本层仅有 `.gitkeep` 等占位文件 | `EMPTY_REQUIRED_DIR` | warning |
| 本层有非占位文件，或有非 skip 子目录 | — | 通过 |

只检查目录**本层**；有子目录即视为非空，不递归统计子目录内文件。

## 4. 插件形态（blocker）

在整包场景下，对源码根内全部 `.py` 做 AST 分析：

| 布局 | 源码扫描根 |
|------|------------|
| 中间 | `00temp/<pkg>/src/` |
| 正式 | `NIMM/<kind>/<pkg>/` |

**具体插件类**：类名不是 `BasePlugin` / `PostProcessingPlugin`，且（直接或间接）继承二者之一。`utils/` 子目录参与继承图解析，但不要求其中类满足业务插件形态。

**对每个具体插件类检查**：

- 须定义 `__init__`（无参可为空实现）→ `PLUGIN_MISSING_INIT`
- 须定义非空 `process`（不能仅有 docstring / `pass` / `...`）→ `PLUGIN_MISSING_PROCESS` / `PLUGIN_EMPTY_PROCESS`
- 源码根内至少一个具体插件（非 utils）→ 否则 `NO_CONCRETE_PLUGIN`

**其它**：

- 包内定义的 `PostProcessingPlugin` 若未直接继承 `BasePlugin` → `PLUGIN_BASE_CHAIN`（warning）

无包时的弱插件检查见第 2.4 节，不触发 `NO_CONCRETE_PLUGIN`。

## 5. 规则一览

### 5.1 阻断项（blocker）

| 规则 ID | 说明 |
|---------|------|
| `CREDENTIAL_PATTERN` | 文本含 PEM 私钥头或典型 AWS Access Key（`AKIA` + 16 位） |
| `MISSING_REQUIRED_DIR` | 中间包缺少包内必要子目录 |
| `MISSING_REQUIRED_DIR_OFFICIAL` | 正式包缺少六树之一 |
| `NO_CONCRETE_PLUGIN` | 整包场景下源码根内无合格具体插件类 |
| `PLUGIN_MISSING_INIT` | 具体插件类缺少 `__init__` |
| `PLUGIN_MISSING_PROCESS` | 具体插件类缺少 `process` |
| `PLUGIN_EMPTY_PROCESS` | `process` 为空实现 |
| `PYTHON_SYNTAX_ERROR` | `.py` 无法 `ast.parse` |
| `PACKAGE_NO_ENTRY_DIR` | 中间包路径下同时缺少 `src/` 与 `cli/` |

### 5.2 警告项（warning）

| 规则 ID | 说明 |
|---------|------|
| `HARDCODED_BIZ_PATH` | 硬编码 `/home/nimm` 或 `/home/<user>/nimm` |
| `PLUGIN_FILE_IO` | 源码 `.py` 非注释行出现 `open(`、`read_csv(` 等（中间 `src/`，正式及 `NIMM/` 含 utils） |
| `DANGEROUS_API` | `eval`/`exec`/`os.system`/`pickle.load`/`subprocess.*` 等 |
| `UNDECLARED_NATIVE_BINARY` | 包相关树内 `.so`/`.pyd`/`.dll` 未在 docs 中说明 |
| `FLAKE8` | flake8 + pep8-naming，行宽 120 |
| `PLUGIN_BASE_CHAIN` | `PostProcessingPlugin` 未直接继承 `BasePlugin` |
| `EMPTY_REQUIRED_DIR` | 必要目录已存在但无实质内容 |

规则元数据（标题、说明文案）在 `rules.py` 的 `RULES` 中维护。

## 6. 扫描范围与忽略

| 项 | 说明 |
|----|------|
| 整包 flake8 | 识别到算法包时，对该包相关**已存在**树下全部纳入扫描的 `.py` 执行 |
| 无包 flake8 | 仅本次变更的 `.py` |
| 跳过目录 | `.git`、`__pycache__`、`.ipynb_checkpoints`、`.pytest_cache`、`.mypy_cache`、`node_modules` |
| 跳过后缀 | `.pyc`、常见图片、`.nc`、`.grib`、`.grb` 等 |
| 文本大小上限 | 约 1MB，超出则不读入做内容规则 |
| Actions 注解 | blocker → `::error`；warning → `::warning` |

## 7. 触发与本地命令

### 7.1 CI 触发

- **Pull Request**（`opened` / `synchronize` 等）：`--base` 为 PR 基线 SHA，按变更识别包并检查
- **手动 workflow_dispatch**：不传 `--base`，通常无包、无 blocker，用于验证流水线

### 7.2 本地命令

```bash
pip install -r .github/scripts/review/requirements.txt
python .github/scripts/review/l1_review.py --path 00temp/demo_algo_clean --json l1-review.json
python .github/scripts/review/format_l1_comment.py --json l1-review.json --out l1-review-comment.md --attempt 1
```

`--path` 可重复；本地指定路径时不依赖 git diff，直接对该包做整包检查。`l1-review.json` 默认在仓库根目录生成（已在 `.gitignore`）。

## 8. 报告、评论与 Artifact

### 8.1 `l1-review.json`

```json
{
  "gate": "l1",
  "packages": ["00temp/demo_algo_issues"],
  "summary": { "blocker_count": 1, "warning_count": 2 },
  "blockers": [
    {
      "rule_id": "MISSING_REQUIRED_DIR",
      "severity": "blocker",
      "path": "00temp/demo_algo_issues",
      "line": null,
      "message": "缺少必要目录: test, nbs, resource"
    }
  ],
  "warnings": []
}
```

`packages` 为空表示本趟未识别到算法包（可能仍有文件级 findings）。

### 8.2 PR 评论

在 **`opened`** 或 **`synchronize`** 且 **`run_attempt == 1`** 时追加一条评论（不覆盖历史）。Re-run 不发评论。

评论含：第 N 次标记、北京时间、阻断/警告摘要、包列表、提交 SHA、Actions 链接。隐藏标记：`<!-- nimm-l1-review -->`。

### 8.3 Artifact

- 名称：`l1-review-report-<run_id>`
- 内容：`l1-review.json`、`l1-review-comment.md`（若生成）
- 用途：供 L2 job 下载 `l1-review.json` 作摘要输入

---

## 9. 处置要求

1. 存在 **blocker**：修复后重新 push；分支保护若要求本检查通过，则不可合并。
2. 仅有 **warning**：job 可通过，合并前仍建议修复（尤其硬编码路径、源码 I/O）。
3. 回溯：按 PR 时间线阅读历次 L1 评论，对照 SHA 与对应 Artifact。
