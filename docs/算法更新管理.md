# 算法代码更新管理

本模块用来 **规划、跟进、发布** 算法代码的优化和修复。代码仍用 Git 保存；GitHub 上用 Issue 记「要做什么」、用 PR 提交改动、用 Milestone 归到某一版、用 Tag / Release 对外宣布版本。

代码能不能进 `main`，由 [算法审核](./算法审核规范.md)（静态检查 + LLM审核）在 **PR** 上完成，与本模块分开。

| 文件 | 作用 |
| ------ | ------ |
| `.github/ISSUE_TEMPLATE/algo-update.yml` | 新建需求时的表单 |
| `.github/pull_request_template.md` | 新建 PR 时的描述草稿 |
| `.github/workflows/issue-progress.yml` | 正式 PR 上，把「代码改了啥」写到已关联的 Issue |
| `.cursor/skills/algo-release/SKILL.md` | 助手协助打整仓 `vX.Y.Z`（须人确认） |

---

## 1. 一次改动怎么走完

典型路径如下。小修可以没有 Issue，直接开 PR（删掉描述里的 `Fixes #`）。

1. **开 Issue**（New issue → **算法优化或修复**）  
   写清这一次要完成什么、清单里有哪些项。右侧选择 **Milestone**（见第 3 节）。
2. **开分支并提 PR**  
   描述第一行填 `Fixes #编号`。需要继续改时可用草稿 PR；L1/L2 在草稿上也会跑。
3. **跟进度**  
   各项是否完成：在 Issue「本次项」和验收里勾选。  
   代码改了什么：看 PR 的文件变更；正式 PR 还会在 Issue 下自动留一段文字说明。
4. **合入**  
   审核通过后合并。写了 `Fixes #编号` 时，GitHub 会关掉对应 Issue。这只表示这件需求在工程上结束，**不会**自动打出版本号。
5. **发版**  
   准备对外发布时，由人打一个整仓 Tag（如 `v1.2.1`）并创建 GitHub Release。

```text
Issue（计划与验收）  ←→  PR（代码与 L1/L2）  →  合入 main  →  人打 vX.Y.Z
         ↑
    Milestone（打算进哪一版）
```

## 2. 分别看哪里

| 问题 | 去哪看 |
| ------ | -------- |
| 打算做什么、各项是否完成 | 那张 **Issue**（「本次项」和验收需人勾选） |
| 具体改了哪些文件、检查过没有 | **PR**（Files changed、Checks） |
| 这一推代码大概改了什么 | Issue 时间线上的自动评论（仅正式 PR；正文含北京时间） |
| 哪些需求计划进同一版 | **Milestone**（如 `v1.3.0`） |
| 已经对外发布的是哪一版、发布说明 | **Releases**（Tag `vX.Y.Z`） |
| 某插件历史上做过哪些需求 | 在 Issues 搜索框输入包名等标题/正文里的字，可再加 `milestone:v1.3.0`。若已打标签，也可以写 `label:bug` |

一张 Issue 写清 **这一次要完成的工作**。「本次项」里可以列出多个相关改动（一个或多个包）。下一次独立的优化或修复请另开 Issue。

## 3. 需求 Issue

### 3.1 新建

1. 点 New issue，选择模板 **算法优化或修复**（有多个模板时需要点选后才会套用）。
2. 在右侧选择 **Milestone**。还没有对应版本时，先到 Issues → Milestones 新建（例如 `v1.3.0`），再填写本表。
3. 标题概括这次工作的意图，例如「降低夜间误报」。
4. 按表单填写类型、目标、本次项、验收。本次项中按条列出要完成的改动，需要时写上包路径。

完成后请在对应项前打勾。机器不会代勾。

### 3.2 Milestone 是什么

Milestone 是 GitHub 自带的「版本篮子」：把若干 Issue（也可以把 PR）标成同一版，例如都进 `v1.3.0`。

- 用来 **区分和筛选** 不同版本的规划与历史，例如搜索 `milestone:v1.3.0` 或 `milestone:v1.3.0 is:closed`。
- 一张 Issue 或 PR **同时只能属于一个** Milestone。
- 截止日期只是计划完成日，到期不会自动关 Issue、也不会自动发版。
- 进度条表示这个篮子里关了多少张 Issue，只供参考。仓库里其它还开着的 Issue 不影响你发布当前这一版。

真正对外的版本号是后面打的 Tag，不是 Milestone 的名字本身。二者建议起成一样（都叫 `v1.3.0`），便于对照。若某张单中途改挂到下一版，它只会出在新 Milestone 的筛选结果里。

## 4. Pull Request

进 `main` 的算法改动请走 PR，以便跑 L1/L2。

- 一件需求对应一个 PR。描述里写 `Fixes #12`（也可用 `Closes`、`Resolves`）。合入后 GitHub 会关闭 Issue #12。
- `Refs #12` 只会留下引用，**不会**关单，适合「提到了、但那张需求还没做完」。
- 没有事先开 Issue 时，删掉模板里的 `Fixes #` 一行即可。
- 也可以在 PR 右侧 Development 里点选 Issue。若没有关闭关键字，合入后需要自己关 Issue。
- L1/L2 的报告只出现在 PR 上。

**草稿 PR** 表示代码还没准备好让人合并，但分支已经在、检查可以先跑。L1/L2 对草稿和正式 PR 都会执行。等到点 **Ready for review** 变成正式 PR 之后，才会把「改了啥」写到 Issue 上（见下一节）。

草稿阶段如果已经写了 `Fixes #` 或在 Development 里点过关联，Issue 与 PR 会立刻连上，只是那时还没有自动进展评论。

## 5. Issue 上的自动进展说明

工作流 `.github/workflows/issue-progress.yml` 在 **正式 PR**（非草稿）上运行：根据本次代码 diff 写一段中文说明，评论到 **已经关联** 的需求 Issue（描述里的 `Fixes` / `Closes` / `Resolves`，或右侧 Development）。没有关联就不写，也不会新开 Issue。

GitHub **不会**在 Development 里点关联时推送 webhook，因此只点 Connect 不会立刻写评论，要等下表里某一次会跑的时机。

| 何时 | 写到哪些 Issue | 说明的是哪一段改动 |
| ------ | ---------------- | ------------------- |
| 打开正式 PR，或草稿变为 Ready | 当前已关联、且还没有本提交评论的 | 相对**目标分支**（PR 要合入的那条，一般为 `main`）的全部改动 |
| 正式 PR 上再 push | 当前已关联、且还没有本提交评论的 | 只这一次 push（合入目标分支带进来的文件会去掉，避免写进别人的改动） |
| 改标题或描述 | 当前已关联、且还没有当前 head 这条评论的 | 相对目标分支的当前全部改动 |

「要不要写」看该 Issue 上有没有同一条 PR、同一个提交 SHA 的进展评论，不比较描述改前改后，也不要求这次新写了 `Fixes #`。已经写过同一 SHA 的不重复写；还缺这条的会补上（例如事后加了 `Fixes #`，或只在 Development 里点过、之后又改了标题/描述）。

因此：事后只在 Development 里点上、接下来**只 push、不改描述**，新 Issue 只会收到「这一推」；若点完后改了标题或描述，会按相对目标分支的整段补一条。

多人并行时，别人的需求合进 `main` 后，请把 `main` **merge 进自己的 PR 分支**再继续推，以免冲突堆到最后。再 push 时：第一份是上一推→当前 head；第二份是**此刻 `main` 的尖**→当前 head（会 `git fetch` 目标分支，不用开 PR 时记下的那个基节点）。交集里才会去掉 merge 带进来、已经和当前 `main` 相同的文件。

评论标题统一为 `PR #编号`，正文含北京时间（`+0800`）、路径，以及 `本次修改：` 一节。有 LLM 时该节为「本次修改：短标题」加说明正文；没有密钥或调用失败时只保留「本次修改：」，正文改为提交说明与路径列表。评论不勾选清单、不粘贴 L1/L2。

摘要使用与 L2 相同的 `OPENAI_API_KEY`（可选 `OPENAI_BASE_URL`、`OPENAI_MODEL`）。生成前会读取该 Issue 的标题和正文（含「本次项」）作为上下文；读失败则只根据 diff 写。

本地可跑同步逻辑的单测（不访问 GitHub）：

```bash
python .github/scripts/release/test_issue_sync.py
```

## 6. 整仓发版

本仓库当作 **一个库** 使用，类似一个 pip 包，只有一条版本线。Tag 格式为 `v` + 三段数字，例如 `v1.2.1`。每个 GitHub Release 对应一个这样的 Tag。不为单个算法包单独打 Tag。

**合入 PR 不会自动产生新版本。** 一次合入只完成一张（或几张）需求；其它仍在进行的需求可以继续留在各自的 Milestone 里。需要对外发布时再打 Tag。

版本号怎么升（语义化版本 SemVer）：

| 改动性质 | 升哪一段 | 例子 |
| ---------- | ---------- | ------ |
| 修复、性能、文档，使用方式不变 | 第三段 patch | `v1.2.0` → `v1.2.1` |
| 兼容的新能力 | 第二段 minor | `v1.2.1` → `v1.3.0` |
| 使用方式不兼容 | 第一段 major | `v1.3.0` → `v2.0.0` |

若本次只改了 CI、公共 `NIMM/utils` 或仓库根文档，可以本轮不打 Tag。发版说明只写功能变化。

操作上可用 `gh release create vX.Y.Z …`，或让助手按 `.cursor/skills/algo-release/SKILL.md` 起草（仍须人确认后才创建）。发版前可以扫一眼对应 Milestone 里的 Issue 是否都已关闭，这只是核对清单。
