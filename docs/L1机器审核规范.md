# L1 机器审核规范

本文档描述本仓库当前已落地的 **L1（机器）算法上传审核** 规则、触发方式、结果产出与处置要求。  
实现代码位于 `.github/scripts/review/`，工作流为 `.github/workflows/l1-review.yml`。  
规则以代码为准；若文档与代码不一致，以 `rules.py` / `review.py` 为准并应回写本文档。

目录结构约定对齐算法仓库 `CODEX.md`（必要子目录：`src`、`cli`、`test`、`docs`、`nbs`、`resource`）。

---

## 1. 目标与范围

| 项目 | 说明 |
| ------ | ------ |
| 门禁级别 | L1（纯机器检查，不含人工签核、不含 LLM） |
| 审核对象 | PR 变更所涉及的算法包 |
| 包路径 | `00temp/<算法名>/`（中间整理目录）或 `NIMM/<算法种类>/<算法名>/`（正式归档目录） |
| 不在范围内 | 大体积二进制样例数据（如 `.nc`/`.grib` 等跳过内容扫描）、人工 checklist、LLM 语义评审 |

L1 之后可扩展 L2（LLM）、L3（人工）；本文档仅覆盖 L1。

---

## 2. 触发与执行流程

### 2.1 何时运行

- **创建或更新 Pull Request**（GitHub 事件 `pull_request`）  
  - 「打开」= 新建 PR（例如点 Create pull request）  
  - 「更新」= 向该 PR 所属分支再次 `push`、或 Re-run 等再次触发同一类事件  
- **在 Actions 页手动触发**（`workflow_dispatch`）  
  - 当前 workflow **不会**传入 `--base` / `--path`  
  - 因此识别不到算法包：`packages` 为空，`blocker_count` / `warning_count` 均为 0，Checks **绿灯通过**，但**没有实质检查**  
  - 也不会发 PR 评论（仅 `pull_request` 事件才追加评论）  
  - 手动触发适合验证 workflow 能否跑通，不适合代替 PR 审核

### 2.2 扫描范围（PR 场景）

1. 计算相对 PR 基线（`base.sha`）的 **变更文件列表**（`git diff --name-only`）  
2. **根据变更文件路径解析算法包根**（是的：改包内任意一个文件即可定位到包）：  
   - `00temp/<pkg>/...` → 包根 `00temp/<pkg>`  
   - `NIMM/<kind>/<pkg>/...` → 包根 `NIMM/<kind>/<pkg>`  
3. 包根下存在 `src/` 或 `cli/` 时，视为算法包，并对该包做 **整包检查**（目录结构 + 包内文件内容规则 + 包内相关 `.py` 的 flake8），不只检查你改过的那一个文件  
4. 若变更文件落在算法包路径之外（且解析不出包），则仅对变更文件做内容类规则扫描（凭据、硬编码路径等），不做「必要目录」整包结构检查  

### 2.3 本地命令

```bash
pip install -r .github/scripts/review/requirements.txt
python .github/scripts/review/review.py --path 00temp/demo_algo_clean --json review.json
python .github/scripts/review/format_comment.py --json review.json --out review-comment.md --attempt 1
```

- `--json review.json`：**会在当前仓库根目录写出/覆盖** `review.json`（可用其他路径；该文件已在 `.gitignore` 中，默认不会提交）  
- `format_comment.py` 会再写出 `review-comment.md`（同样可本地预览评论正文，默认已 gitignore）  
- `--path` 可重复，指定多个包；本地指定路径时不依赖 git 变更列表，直接整包检查  

### 2.4 结果处置流水线（PR）

1. 运行检查 → 写出 `review.json`  
2. 渲染 PR 评论 Markdown（含北京时间、第 N 次）  
3. 上传 Artifact：`l1-review-report-<run_id>`（含 `review.json`、`review-comment.md`）  
4. 在 PR **追加**一条评论（不覆盖历史评论）  
5. 若存在 **阻断项（blocker）** → Job 失败（Checks 红灯）；仅有警告则绿灯

## 3. 严重级别定义

| 级别 | 英文 | 对 Checks 的影响 | 对合并的影响 |
|------|------|------------------|--------------|
| 阻断 | `blocker` | 失败（红灯） | 若分支保护要求本检查通过，则不可合并 |
| 警告 | `warning` | 不单独失败 | 可合并，但应修复后再入库 |

评论与 `review.json` 中均会列出全部阻断项与警告项。

---

## 4. 必要目录（结构门禁）

每个算法包（无论中间目录还是正式目录）**必须同时具备**以下子目录：

| 目录 | 用途（与 CODEX 一致） |
| ------ | ------------------------ |
| `src/` | 核心算法 / 插件源码 |
| `cli/` | 调度与预处理入口 |
| `test/` | 单元测试 |
| `docs/` | 说明文档 |
| `nbs/` | notebook 示例 |
| `resource/` | 资源与小规模测试用资源（可先空目录 + `.gitkeep`） |

可选（当前 L1 **不**强制）：`utils/`、`test_data/`（测试数据建议放独立 testdata 仓）。

| 规则 ID | 适用路径 | 级别 |
|---------|----------|------|
| `MISSING_REQUIRED_DIR` | `00temp/<pkg>/` | **阻断** |
| `MISSING_REQUIRED_DIR_OFFICIAL` | `NIMM/<kind>/<pkg>/` | **阻断** |

缺任一必要目录即记一条对应规则（message 中列出缺失目录名）。

## 5. 规则一览

### 5.1 阻断项（blocker）

| 规则 ID | 标题 | 检查要点 |
| --------- | ------ | ---------- |
| `CREDENTIAL_PATTERN` | 疑似凭据或私钥 | 文本中出现 PEM 私钥头（`BEGIN … PRIVATE KEY`）或典型 AWS Access Key 形态（`AKIA` + 16 位） |
| `MISSING_REQUIRED_DIR` | 中间目录缺少必要子目录 | 见第 4 节 |
| `MISSING_REQUIRED_DIR_OFFICIAL` | 正式目录缺少必要子目录 | 见第 4 节 |

### 5.2 警告项（warning）

| 规则 ID | 标题 | 检查要点 |
| --------- | ------ | ---------- |
| `HARDCODED_BIZ_PATH` | 硬编码业务路径 | 出现 `/home/nimm` 或 `/home/<user>/nimm` 一类路径 |
| `PLUGIN_FILE_IO` | src 中疑似文件 I/O | `src/**/*.py` 非注释行出现 `open(`、`read_csv(`、`to_csv(`、`Path(...).write` 等 |
| `UNDECLARED_NATIVE_BINARY` | 未说明的二进制扩展 | 包内存在 `.so` / `.pyd` / `.dll`，且 `docs/` 中未提及该文件名或后缀 |
| `FLAKE8` | flake8 风格与格式问题 | 对本次纳入扫描的 `.py` 跑 flake8（**行宽 120**），覆盖 PEP 8 相关风格与格式（缩进、行宽、未使用变量、简单语法问题等）；**不再使用 Black** |

说明：

- 插件 I/O、硬编码路径在业务迁移期仍可能出现，故暂为警告；正式入库前应清理。  
- 风格/格式统一以 flake8 为准，建议修复，当前不阻断，避免历史代码一次性红灯过多。  
- 在「识别到算法包」时，flake8 作用范围为**该包内所有被扫描到的 `.py`**（整包），不是只查你改动的那一个文件。

## 6. 扫描与忽略策略

| 策略 | 说明 |
| ------ | ------ |
| 跳过目录名 | `.git`、`__pycache__`、`.ipynb_checkpoints`、`.pytest_cache`、`.mypy_cache`、`node_modules` |
| 跳过后缀（不做文本规则扫描） | `.pyc`、图片、`.nc`、`.grib`、`.grb` 等 |
| 单文件大小上限 | 超过约 1MB 的文本不读入做内容规则匹配 |
| 注解 | 在 Actions 日志 / Checks Annotations 中输出 `::error`（阻断）或 `::warning`（警告） |

## 7. 报告与审计产物

### 7.1 `review.json`（机器可读）

主要字段：

```json
{
  "gate": "l1",
  "packages": ["00temp/demo_algo_issues"],
  "summary": { "blocker_count": 1, "warning_count": 2 },
  "blockers": [
    {
      "rule_id": "MISSING_REQUIRED_DIR",
      "severity": "blocker",
      "path": "00temp/demo_algo_issues",
      "line": null,
      "message": "缺少必要目录: test, nbs, resource"
    }
  ],
  "warnings": []
}
```

### 7.2 PR 评论（人可读时间线）

- 每次检查 **追加** 新评论，不覆盖历史  
- 标题含「第 N 次」；正文含 **检查时间（北京时间 +0800）**、状态、包列表、阻断/警告摘要、**提交 SHA**、**Actions 运行链接**  
- 隐藏标记：`<!-- nimm-l1-review -->`（用于统计次数，不对用户展示）

字段含义：

| 评论字段 | 含义 |
| ---------- | ------ |
| 提交 | 本次检查对应的 Git commit SHA（代码版本） |
| Actions 运行 | 本次 workflow run 页面；可下该次 Artifact |
| run_id | Actions 运行数字 ID，出现在 Artifact 名 `l1-review-report-<run_id>` 中 |

### 7.3 Artifact

- 名称：`l1-review-report-<run_id>`  
- 内容：该次运行的 `review.json`、`review-comment.md`  
- 保留：默认随 GitHub Artifact 策略（通常约 90 天）；**每一次 run 各自一份**，不是只保留最近一次  
- 历史回顾：打开对应次数评论里的 Actions 链接，或在 Checks 中点开历史运行

---

## 8. 开发者处置要求

1. **有阻断**：必须修复后再次 push；Checks 变绿前不应合并（建议开启分支保护强制本检查）。  
2. **仅有警告**：Checks 可通过，但仍应在合并前尽量消除（尤其硬编码路径、src 内文件 I/O）。  
3. **回溯**：按 PR Conversation 时间线阅读历次 L1 评论，对照提交 SHA 与 Artifact。
