# 算法审核规范

算法代码合入 `main` 前，由本模块在 PR 上做一次审核：一条工作流、一条评论。

- 脚本：`.github/scripts/review/`
- CI：`.github/workflows/algorithm-review.yml`

评论分两节：**静态检查**（规则阻断与警告）和 **LLM审核**（总评与发现）。GitHub Checks 名称仍是 `L1 machine review`、`L2 LLM review`，评论里不写 L1、L2。

文档与代码不一致时，以 `rules.py`、`l1_review.py`、`l2_review.py` 为准，并改本文。合入之后的规划与发版见 [算法更新管理](./算法更新管理.md)，不在本模块。

---

## 1. 模块与流程

| | 静态检查（job `l1`） | LLM审核（job `l2`） |
| -- | ---------------------- | --------------------- |
| 做什么 | 目录结构、语法、插件形态、密钥、flake8 等规则 | 看语义和工程意图，给人工参考；不替代静态检查，也不替代人终审 |
| 产出 | `l1-review.json`、先发出的 PR 评论、Actions 注解 | `l2-review.json`、更新同一条评论里的 LLM审核节 |
| 何时失败 | 有 **blocker** 则 job 失败；**warning** 只记录 | 发现项本身不让 job 失败。未配置 API Key，或调用/解析失败时例外 |
| 看什么 | PR 相对基线的变更，或本地 `--path` | 算法包文本、未成包的变更文件，以及静态检查报告摘要 |

```text
Pull Request / 手动触发
  ├─ job l1  静态检查 → Artifact（含 l1-review.json）→ 发出审核评论
  │            └─ 有 blocker → job 失败，本 run 不再跑 l2
  └─ job l2  等 l1 成功 → 下载 l1-review.json → 调用 LLM → Artifact
               → 更新同一条评论的「LLM审核」节
```

- 开 PR（含草稿）或在 Actions 里手动跑 **Algorithm review** 都会触发。
- LLM 只用静态检查产出的 `l1-review.json` 作摘要，不会在 l2 里再跑一遍规则。

**分支保护不是脚本里的开关。** 工作流每次都会跑检查；拦不拦合并，要在 GitHub 仓库 **Settings → Rules / Branches → 分支保护规则** 里勾选「必须通过的 status checks」。建议勾上 **`L1 machine review`**。**`L2 LLM review`** 一般不要勾——没配 `OPENAI_API_KEY` 或调用失败时这个 Checks 会红，勾上之后就合不进去。只有明确要求每次 PR 都必须跑通 LLM 时，再勾 L2。改 Python 或 workflow 文件不会自动变成「必过」。

**下面这些情况不会调用 LLM：**

| 情况 | 结果 |
| ------ | ------ |
| 静态检查有 blocker | 本 run 不启动 l2 |
| 没有算法包，也没有可读的变更文件 | 仍写出报告，`skipped: true`（见下） |
| 未配置 API Key | 写出报告，`skipped: true`，job 失败 |
| API 调用失败，或模型输出无法解析成 JSON | 写出报告，`skipped: true`，job 失败 |
| `--dry-run` | 不调模型，只验证报告格式 |

「没有算法包、也没有可读变更」**不是**「先开 PR 再把改动撤掉」那种用法。常见来源是：

- 在 Actions 页手动跑 workflow（`workflow_dispatch`），没有 PR diff，通常也就没有包、没有变更文件。
- PR 只动了审核不读的文件，例如图片、`.nc` / `.grib`、或 git 记为删除、不在 Added/Copied/Modified/Renamed 里的路径。

普通改算法包或改 `.py` / `.md` 的 PR 不会走到这一支。

**会调用 LLM 的前提：** 静态检查已通过，并且 API 可用。此时只要本次变更里有可读材料就会调用，例如：

- 识别到了算法包
- 没识别到包，但改了公共库（如 `NIMM/utils`）、文档或脚本
- 上面两种同时出现

合入前由人根据 LLM 的发现项做最终判断。

## 2. 算法包识别

静态检查和 LLM审核用同一套包发现（`common.py`）。目录约定与算法仓库 `CODEX.md` 一致。

### 2.1 两类布局

**中间目录（整理期）**

```text
00temp/<pkg>/
  src/ cli/ test/ docs/ nbs/ resource/
```

**正式目录（归档后）**

```text
NIMM/<kind>/<pkg>/              # 源码根（插件扫描根）
cli/<kind>/<pkg>/               # 调度入口
test/<kind>/<pkg>/
docs/<kind>/<pkg>/
nbs/<kind>/<pkg>/
resource/<kind>/<pkg>/
```

正式算法的稳定标识是 **`NIMM/<kind>/<pkg>`**。配套目录与 `NIMM` 在仓库根同级。源码直接放在 `NIMM/<kind>/<pkg>/` 下，里面不必再套一层 `src/` 或 `cli/`。

### 2.2 从变更路径解析包

| 变更路径前缀 | 识别结果 |
| -------------- | ---------- |
| `00temp/<pkg>/...` | 中间包 `00temp/<pkg>` |
| `NIMM/<kind>/<pkg>/...` | 正式包 `NIMM/<kind>/<pkg>` |
| `cli\|test\|docs\|nbs\|resource/<kind>/<pkg>/...` | 同上，仍是这个正式包 |
| `NIMM/utils/...` | 公共库，**不**算算法包 |
| `NIMM/<kind>/...`（没有 pkg 这一层） | 不算算法包 |
| 其它路径 | 不算算法包 |

### 2.3 何时做整包检查

**中间包：** 路径能解析成 `00temp/<pkg>`，并且包内已有 `src/` 或 `cli/`。路径像中间包、但这两个目录都没有时，记 **`PACKAGE_NO_ENTRY_DIR`**（blocker），不做整包检查。

**正式包：** 路径符合第 2.2 节的正式包规则，即做整包检查。

整包静态检查覆盖：必要目录、空目录警告、插件形态、二进制说明、相关树里的文件内容规则，以及 flake8。

### 2.4 没有识别成算法包时

变更落在算法包路径之外（例如 `NIMM/utils`、文档、CI 脚本）时：

- **静态检查**仍检查本次改动的文件：语法、凭据、硬编码路径、flake8；`NIMM/**` 下 `.py` 的疑似文件 I/O；危险 API。另外做弱插件检查：只在本次变更的 `.py` 里解析继承，不要求「包里至少有一个具体插件」。
- **LLM审核**仍会按这些变更文件调用模型（见第 4 节）。静态检查本身不做语义判断。

## 3. 静态检查

### 3.1 必要目录（结构门禁）

**中间包 `00temp/<pkg>/`** 必须同时有下面这些包内子目录，缺一个就是 blocker（规则 **`MISSING_REQUIRED_DIR`**）：

| 目录 | 用途 |
| ------ | ------ |
| `src/` | 插件与算法源码 |
| `cli/` | 调度入口 |
| `test/` | 单元测试 |
| `docs/` | 说明文档 |
| `nbs/` | notebook |
| `resource/` | 资源（可以先放 `.gitkeep`） |

**正式包 `NIMM/<kind>/<pkg>`** 必须同时有下面六处路径，缺一个就是 blocker（规则 **`MISSING_REQUIRED_DIR_OFFICIAL`**）：

| 路径 | 用途 |
| ------ | ------ |
| `NIMM/<kind>/<pkg>/` | 源码根 |
| `cli/<kind>/<pkg>/` | 调度入口 |
| `test/<kind>/<pkg>/` | 单元测试 |
| `docs/<kind>/<pkg>/` | 说明文档 |
| `nbs/<kind>/<pkg>/` | notebook |
| `resource/<kind>/<pkg>/` | 资源 |

`NIMM/utils/` 这类公共库不做上面的六树门禁。

目录已经存在时，再看本层有没有实质内容（缺目录仍由上一节的 blocker 处理）：

| 情况 | 规则 | 级别 |
| ------ | ------ | ------ |
| 本层没有文件，也没有子目录 | `EMPTY_REQUIRED_DIR` | warning |
| 本层只有 `.gitkeep` 等占位文件 | `EMPTY_REQUIRED_DIR` | warning |
| 本层有非占位文件，或有未跳过的子目录 | — | 通过 |

只看目录**本层**。有子目录就算非空，不往下数子目录里的文件。

### 3.2 插件形态（blocker）

整包检查时，对源码根里全部 `.py` 做 AST 分析：

| 布局 | 源码扫描根 |
|------|------------|
| 中间 | `00temp/<pkg>/src/` |
| 正式 | `NIMM/<kind>/<pkg>/` |

**具体插件类：** 类名不是 `BasePlugin` / `PostProcessingPlugin`，并且直接或间接继承二者之一。`utils/` 子目录会参与继承图，但不要求那里的类也满足业务插件形态。

对每个具体插件类：

- 必须有 `__init__`（可以无参、可以为空实现）→ 否则 `PLUGIN_MISSING_INIT`
- 必须有非空 `process`（不能只有 docstring、`pass` 或 `...`）→ 否则 `PLUGIN_MISSING_PROCESS` / `PLUGIN_EMPTY_PROCESS`
- 源码根里至少要有一个具体插件（不含 utils）→ 否则 `NO_CONCRETE_PLUGIN`

包内自己定义的 `PostProcessingPlugin` 若没有直接继承 `BasePlugin`，记 `PLUGIN_BASE_CHAIN`（warning）。没有算法包时的弱插件检查见第 2.4 节，不触发 `NO_CONCRETE_PLUGIN`。

### 3.3 规则一览

**阻断项（blocker）**

| 规则 ID | 说明 |
| --------- | ------ |
| `CREDENTIAL_PATTERN` | 文本含 PEM 私钥头，或典型 AWS Access Key（`AKIA` + 16 位） |
| `MISSING_REQUIRED_DIR` | 中间包缺少包内必要子目录 |
| `MISSING_REQUIRED_DIR_OFFICIAL` | 正式包缺少六树之一 |
| `NO_CONCRETE_PLUGIN` | 整包检查时，源码根里没有合格的具体插件类 |
| `PLUGIN_MISSING_INIT` | 具体插件类缺少 `__init__` |
| `PLUGIN_MISSING_PROCESS` | 具体插件类缺少 `process` |
| `PLUGIN_EMPTY_PROCESS` | `process` 是空实现 |
| `PYTHON_SYNTAX_ERROR` | `.py` 无法 `ast.parse` |
| `PACKAGE_NO_ENTRY_DIR` | 中间包路径下同时没有 `src/` 和 `cli/` |

**警告项（warning）**

| 规则 ID | 说明 |
| --------- | ------ |
| `HARDCODED_BIZ_PATH` | 硬编码 `/home/nimm` 或 `/home/<user>/nimm` |
| `PLUGIN_FILE_IO` | 源码 `.py` 非注释行出现 `open(`、`read_csv(` 等（中间扫 `src/`，正式扫 `NIMM/`，含 utils） |
| `DANGEROUS_API` | `eval` / `exec` / `os.system` / `pickle.load(s)`；普通 `subprocess` 列表调用不在此列；`.github/scripts/review/` 不做此项，也不扫硬编码路径 |
| `UNDECLARED_NATIVE_BINARY` | 包相关树里的 `.so` / `.pyd` / `.dll` 未在 docs 中说明 |
| `FLAKE8` | flake8 + pep8-naming，行宽 120 |
| `PLUGIN_BASE_CHAIN` | `PostProcessingPlugin` 未直接继承 `BasePlugin` |
| `EMPTY_REQUIRED_DIR` | 必要目录已存在，但没有实质内容 |

规则的标题和说明文案在 `rules.py` 的 `RULES` 里维护。

### 3.4 扫描范围与忽略

| 项 | 说明 |
| ---- | ------ |
| 整包 flake8 | 识别到算法包时，对该包相关、且已经存在的树下全部纳入扫描的 `.py` 执行 |
| 无包 flake8 | 只检查本次变更的 `.py` |
| 跳过目录 | `.git`、`__pycache__`、`.ipynb_checkpoints`、`.pytest_cache`、`.mypy_cache`、`node_modules` |
| 跳过后缀 | `.pyc`、常见图片、`.nc`、`.grib`、`.grb` 等 |
| 文本大小上限 | 约 1MB，超出则不做内容规则 |
| Actions 注解 | blocker → `::error`；warning → `::warning` |

## 4. LLM审核

### 4.1 上下文采集

一次调用可以把多段材料拼进同一个 user prompt。包发现与第 2 节相同。每个识别到的包采集可读文本（`.py`、`.md`、`.txt`、`.rst`），顺序是 **docs → 源码 → cli**。

| 布局 | docs | 源码 | cli |
|------|------|------|-----|
| 中间 | `00temp/<pkg>/docs/` | `00temp/<pkg>/src/` | `00temp/<pkg>/cli/` |
| 正式 | `docs/<kind>/<pkg>/` | `NIMM/<kind>/<pkg>/` | `cli/<kind>/<pkg>/` |

正式算法的 cli 在仓库根 `cli/<kind>/<pkg>/`，源码在 `NIMM/<kind>/<pkg>/`。按这些路径采集，**不要**因为 NIMM 目录里没有 `cli/` 子目录就当成结构问题。

单文件大约 12k 字符、一次调用大约 60k 字符为上限，超出则截断或省略。

**非包变更：** 没有落入任何已识别算法包扫描根的变更文件，单独成一段。标题会标明「非算法包变更」或「未识别到算法包时的变更文件」，内容只含本次变更里的可读文件。要求模型按给定文件做语义和风险核查；材料里没有 cli 或插件时，不要臆造整包结构问题。

**静态检查摘要：** 若有 `l1-review.json`，会把 blocker / warning 摘要附在 prompt 里，供模型参考。模型应避免把静态检查已经判定的条目再罗列一遍。

### 4.2 模型核查要求

System prompt 要求模型只输出**一个 JSON 对象**（不要加 Markdown 围栏），字段包括：

- `risk_level`：`low` | `medium` | `high`
- `overview`：中文总评
- `findings[]`：每条含 `severity`、`category`、`path`、`title`、`detail`、`evidence`

规范与风险标准一致。材料里实际有什么，就查什么；没有的不要编。

**通用（有依据再写）：** 逻辑是否合理、与可见文档是否大致一致、硬编码或隐蔽 I/O、不安全执行，以及其它入库前应让人知道的问题。

| 材料 | 要求 |
| ------ | ------ |
| 含插件 / `process` 等源码 | 评估是否空壳、是否像真实实现 |
| 含可读 cli | 判断是否调用了插件业务；只有占位则写入 findings；没有 cli 就不要查，也不要写「缺 cli」 |
| 结构 / 六树 | 不做静态检查已经负责的结构门禁推断 |

正式算法材料里的 cli，通常在仓库根 `cli/<kind>/<pkg>/`。

**输出约定：** 不要输出 `needs_human_attention`、`human_checklist`。信息不足时 `risk_level` 用 `low`，并在 overview 里说明局限。

### 4.3 配置

| Secret / 变量 | 必填 | 说明 |
| --------------- | ------ | ------ |
| `OPENAI_API_KEY` | 跑 LLM审核时必填 | API Key |
| `OPENAI_BASE_URL` | 否 | OpenAI 兼容网关，默认 `https://api.openai.com/v1` |
| `OPENAI_MODEL` | 否 | 默认 `gpt-4o-mini` |

## 5. PR 评论

在 PR **打开**或 **推送新提交** 时，按分支当前 head SHA 维护 **一条** 审核评论。一轮检查对应这一次提交。

1. 标题用 Markdown **二级标题**：`## 审核 <短 SHA>`。评论已经嵌在 PR 时间线里，再用一级 `#` 会撑得过大，也不像独立文档的篇名。
2. 顶部只写提交、算法包、检查时间、Actions。SHA 和算法包不在正文里再写一遍。
3. 正文分 **静态检查**、**LLM审核** 两节。
4. 静态检查一结束就发出评论；LLM审核节先占位，完成后更新同一条。静态检查未通过时，LLM审核节写「未执行」。
5. 同一 SHA 再跑一次（包括 Re-run）仍更新这一条，不另开「第 N 次」。

**Actions 运行** 链到的是**这一次 workflow 运行页**（`…/actions/runs/<run_id>`），不是单独的 L1 或 L2 job。两个 job 的日志和 Artifact 都在这一页，可分别点开。

页面上看不到的 HTML 标记：`<!-- nimm-review-round:<完整 SHA> -->`，以及两节的槽位注释。完整 JSON 以 Artifact 为准。

下面样例与渲染脚本输出一致，已去掉 HTML 注释。

## 6. 报告与 Artifact

### 6.1 `l1-review.json`

先给一份完整样例，再对照字段。

```json
{
  "gate": "l1",
  "packages": ["00temp/example_pkg"],
  "summary": { "blocker_count": 1, "warning_count": 0 },
  "blockers": [
    {
      "rule_id": "MISSING_REQUIRED_DIR",
      "severity": "blocker",
      "path": "00temp/example_pkg",
      "line": null,
      "message": "缺少必要目录: test, nbs, resource"
    }
  ],
  "warnings": []
}
```

| 字段 | 含义 |
|------|------|
| `gate` | 固定为 `l1` |
| `packages` | 识别到的算法包 ID；为空表示这一趟没有识别到算法包，文件级发现仍可能有 |
| `summary.blocker_count` | 阻断项条数 |
| `summary.warning_count` | 警告项条数 |
| `blockers[]` | 阻断项列表 |
| `warnings[]` | 警告项列表 |
| `blockers[]` / `warnings[]` 每条 | `rule_id`、`severity`、`path`、`line`（可 `null`）、`message` |

### 6.2 `l2-review.json`

结构与上一节相同，先给一份完整样例，再对照字段。

```json
{
  "gate": "l2",
  "packages": ["00temp/example_pkg"],
  "model": "gpt-4o-mini",
  "skipped": false,
  "skip_reason": null,
  "error": null,
  "summary": { "risk_level": "medium", "finding_count": 1 },
  "overview": "插件有真实计算逻辑，但 cli 仅打印占位提示，未调用 process。",
  "findings": [
    {
      "severity": "medium",
      "category": "cli",
      "path": "00temp/example_pkg/cli/run.py",
      "title": "cli 未调用插件业务",
      "detail": "入口只打印 usage，没有 import 或调用 process。",
      "evidence": "if __name__ == \"__main__\": print(\"TODO\")"
    }
  ]
}
```

| 字段 | 含义 |
|------|------|
| `gate` | 固定为 `l2` |
| `packages` | 识别到的算法包 ID，可以为空 |
| `model` | 模型名；dry-run 时为 `dry-run` |
| `skipped` | 是否未调用 LLM |
| `skip_reason` | 跳过原因（没有输入、缺 Key、调用失败等） |
| `error` | 调用失败时的错误信息 |
| `summary.risk_level` | 这一趟的总体风险 |
| `summary.finding_count` | findings 条数 |
| `overview` | 中文总评 |
| `findings[]` | 问题列表，人工主要据此审核 |

| 名称 | 内容 | 用途 |
|------|------|------|
| `l1-review-report-<run_id>` | `l1-review.json`、`l1-review-comment.md`（若生成） | l2 job 下载 `l1-review.json` 作摘要 |
| `l2-review-report-<run_id>` | `l2-review.json`、`l2-review-comment.md`（LLM审核节正文） | 回溯完整 JSON |

## 7. 触发、本地命令与处置

### 7.1 CI 触发

- **Pull Request**（打开、推送等）：`--base` 为 PR 基线 SHA，按变更识别包并检查。
- **手动 workflow_dispatch**：不传 `--base`，通常没有包、也没有 blocker，用来验证流水线能否跑通。

### 7.2 本地命令

```bash
pip install -r .github/scripts/review/requirements.txt

# 静态检查
python .github/scripts/review/l1_review.py --path 00temp/<pkg> --json l1-review.json
python .github/scripts/review/format_l1_comment.py --json l1-review.json --out l1-review-comment.md

# LLM审核（dry-run 不调用模型）
python .github/scripts/review/l2_review.py --path 00temp/<pkg> --dry-run --json l2-review.json
python .github/scripts/review/format_l2_comment.py --json l2-review.json --out l2-review-comment.md

# 调用模型（需环境变量；Windows）
set OPENAI_API_KEY=sk-...
python .github/scripts/review/l2_review.py --path 00temp/<pkg> --json l2-review.json --l1-json l1-review.json

# 仅公共库变更
python .github/scripts/review/l2_review.py --path NIMM/utils --dry-run --json l2-utils.json
```

`--path` 可以写多次。本地指定路径做静态检查时不看 git diff，直接对该包做整包检查。路径解析不成算法包时，LLM审核会把该路径下的文件当作变更上下文（见第 4.1 节）。报告 JSON 默认写在仓库根（已列入 `.gitignore`）。

本仓库以审核脚本和规范文档为主。算法样例请放在独立测试分支，避免故意失败的样例合进 `main` 后把静态检查打红。

### 7.3 处置

1. 有 **blocker**：修好再 push。若分支保护要求这项检查通过，则不能合并。
2. 只有 **warning**：检查可以通过，合并前仍建议修（尤其是硬编码路径、源码里的 I/O）。
3. 回溯：在 PR 时间线上按提交看对应审核评论（标题含短 SHA），需要细节时对照 Artifact。
